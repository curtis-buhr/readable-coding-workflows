Handle cancellation when a destination has accepted a write but its acknowledgement has not yet been checkpointed. Keep the prior public APIs and batch results.

The sink contract now requires idempotent durable effects by the pair (tenant ID, source sequence). Repeated writes for the same pair and payload have only one durable effect, and the sink may acknowledge a replay with true. The same sequence in different tenants identifies different writes. The source payload for a given pair is stable. Use the original tenant ID, sequence, and payload unchanged on every retry. Never infer that a sink committed a write from cancellation or a transient failure.

Both SyncAsync and SyncAllAsync must check the caller's cancellation token immediately after each sink call that returns, before examining the acknowledgement or saving a checkpoint. If the token is canceled, throw OperationCanceledException with that token. An acknowledgement that reaches the caller after cancellation must leave the corresponding checkpoint unchanged, even if the sink has durably applied the write. An OperationCanceledException thrown by the sink must propagate without saving that checkpoint. If the sink throws RetryableSinkException while the caller token is canceled, surface cancellation and stop the entire operation. The rule also applies to SyncAsync.

Previously saved checkpoints remain valid after cancellation. No later record or tenant may be started once cancellation is observed. A fresh engine using the same checkpoint store and sink must replay an uncheckpointed write and advance only after receiving its acknowledgement. Checkpoint Save is synchronous and atomic. Cancellation racing inside Save may leave that already-started Save committed.
